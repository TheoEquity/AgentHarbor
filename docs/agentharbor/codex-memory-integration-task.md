# 让 Codex 用上项目记忆

**已实施。Windows Codex 已在 `testmem` 通过闭环验收。** [实测与独立审查记录](codex-memory-integration-acceptance.md)

## 用户怎么用

1. 在 AgentHarbor 网页选好项目，按页面提示在本机运行一次连接助手，选中平时用 Codex 打开的目录。助手保存项目凭据、合并配置、检查连接，并告诉用户是否还要信任目录、重启或新开会话。默认不用手改配置、设环境变量或另装 Python、Node。
2. 在这个目录开一个新会话，直接交代工作。Codex 发出第一次模型请求前，应该已经拿到少量审核通过的项目知识。需要具体步骤时，Codex 再按需搜索。
3. 用户说“记住这条约定”，或 Codex 在工作中发现值得留下的决定、步骤或纠错，就整理成一条素材。服务端返回 `pending` 和 `request_id` 后，Codex 才告诉用户“已提交，等你审核”。临时工作留在当前会话。
4. 用户在现有网页批准、修改、合并或拒绝素材。下次开新会话，符合启动摘要条件的知识会自动带进来，其他已生效的细节可以搜索。

## 从哪里动手

**先在用户实际用的桌面版本上试。** 记下 Windows Codex 版本、打开的目录和生效的配置。优先试远程 Streamable HTTP MCP，验证桌面端能连上、能安全传递和更新凭据。再验证打开会话后，哪一步能在第一次模型请求前把知识交给模型，以及用什么记录证明这个顺序。按仓库约定运行真实 Agent 测试，CLI 可辅助排查。缺哪项能力就补哪项轻量适配。如果首轮仍做不到，写清卡在哪一步。

**复用已有的记忆服务。** 上次检查时，本地 Python MCP 已有搜索和提交工具。连接脚本能写配置，但要单独配置首轮读取的 Hook。仓库里有首个 `UserPromptSubmit` 的读取逻辑，上次检查的会话没有加载对应工具或 Hook，远程 MCP 也还没实现。开工时复核这些情况。

服务端沿用现有数据库、项目权限、审核和版本规则，提供启动摘要、搜索和提交三种能力。现有摘要约 2,000 字节，只选已生效且无争议的语义记忆，详细步骤和经历按文本搜索。提交方要在**第一次发送前**拿到并保留 `request_id`，直到结果明确。丢了回执就用原 ID 和原内容重试，服务端返回同一条素材的当前状态。不同请求即使意思相近，也不靠这个 ID 去重。

**让连接助手管好本机配置。** 助手私下保存凭据，合并项目配置和启动 Hook。首次运行、重跑和中途失败后再跑，都要保留用户其他设置。助手应说清哪些步骤已成功、哪一步失败、怎么恢复。项目 token 只说明有权访问哪个项目；客户端还要核对实际会话目录，避免项目 B 或未绑定目录误用 A 的工具。现有凭据有效期为 30 天，到期后重新授权，再用同一助手更新并检查连接。

本轮只做 Codex。本机不增加常驻服务、数据库或同步进程。以后接 DeepSeek Harness 时复用同一服务，只适配配置和会话启动，并检查项目 preset 和宿主全局配置各自对哪些会话生效。沿用现有审核网页和授权方式，不改模型地址、代理或项目的 `AGENTS.md`。全量聊天上传、向量库、模型自动提炼、自动批准、通用插件平台和任务派发都在本轮范围外。

## 怎么验收

准备两个独立项目 A、B。在 A 中用一个猜不到的随机值做项目约定，例如某个字段该填什么。只把答案给提交素材的会话。接收端开全新会话，只交代填字段的任务。提示、继承的历史和可读文件都不能泄露答案，验收日志也放在它读不到的位置。

| 要验证什么 | 怎样算通过 |
| --- | --- |
| 第一次接入要做几步？ | 在已装目标 Codex、没有 AgentHarbor 配置、凭据、Hook 或专用运行时的 Windows 环境，从网页入口运行一次助手。选好目录后，新会话能自动读取并使用工具。记下实际操作步数、额外安装、授权和重启情况。再跑一次，仍只有一个绑定，原有其他配置还在。 |
| 第一轮真的用上记忆了吗？ | 在 A 预置一条已批准的约定。分别留三份证据：服务端选了哪条、哪个版本；桌面端在首个模型请求前已把它交给模型的事件或脱敏请求记录；Codex 按约定填对的字段。接收会话不手工搜索或注入答案。 |
| 需要细节时查得到吗？ | 选一条已批准、但没有进入启动摘要的操作步骤。只给任务目标，核对 Codex 调用 `search_project_memory` 的记录、查到的条目版本，以及它实际按步骤做出的结果。 |
| 说“记住”之后发生了什么？ | 让 Codex 用 `submit_project_memory_material` 提交带随机值的新约定。核对待审回执、请求 ID 和素材记录。批准前另开会话，启动摘要里应没有这条约定。 |
| 审核后下次能用吗？ | 在网页批准素材，记录生成的条目和修订。另开全新会话做填字段任务，再取上面的三份证据。修改或合并后应读到生效版本，拒绝的素材不得进入有效知识。 |
| 换个项目会串吗？ | 在已配置 A 的同一台机器打开 B。核对实际目录和绑定，分别试启动读取、搜索和提交，确认都没有读写 A。 |
| 提交成功但回执丢了怎么办？ | 服务端写入后丢弃第一次回执，客户端显示“结果待确认”。用原 ID、原内容重试，应取回同一条素材，审核队列只有一条。用原 ID 改内容应报冲突。用旧版本修改条目也应报冲突，保留较新版本。 |
| 首次读取超时还能工作吗？ | 分别试断网和慢连接，记下等待上限和实际耗时。超时后显示读取失败，对话能继续。恢复连接后，同一会话能按需搜索，下一个全新会话能自动读取。 |
| 到期或停用后会怎样？ | 到期凭据应被拒绝，重新授权并更新后桌面端恢复访问。分别关闭读取、关闭写入、停用条目，检查每项效果，再恢复并复测。 |

交付时附上接入入口和实测记录。用时间及可取得的会话、请求、素材、条目和版本标识把记录对应起来，隐去 token 和授权头。沿用仓库暂停整套 Go 和桌面测试的约定。只有目标桌面端走通上述流程并通过表中检查，才能标为完成；缺了证据就写明哪项待验、影响是什么、由谁跟进。

先前的 2–4 工程周估的是两个客户端。桌面短验证后，再按服务端、连接助手、启动读取和真实验收估算 Codex 单线工期。后续成本包括服务器、额外的上下文 token、人工审核和客户端升级适配。
