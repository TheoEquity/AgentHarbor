# AgentHarbor 第一版实施方案：两机 Codex

整理日期：2026-11-07
状态：A 机本机同步与导入已实现并验收；B 机和完整 M01–M05 待验收

本方案以[完整需求](requirements.md)为目标背景，以[最小验收 M01–M05](acceptance.md)作为第一版交付门槛。当前已完成的 A 机部分及其实际限制见[本机验收记录](local-acceptance-a.md)；代码尚未推送公开仓库，B 机接入后仍需复核。本轮只适配 Codex：A 机模拟云端并运行 Codex，B 机运行另一实例 Codex；两机各自从原有入口开始任务。第一版使用腾讯 MemoryCore 作为项目记忆服务。后续 Agent 仍可沿用适配器边界加入，但不计入本轮交付。

具体组件、数据、接口和 A/B 运行方式见[两机 Codex 技术方案](technical-design-v1.md)。

## 1 数据流与责任

| 位置 | 第一版职责 |
| --- | --- |
| A 机服务 | 网页、API、PostgreSQL 中的项目/机器/任务与记忆身份映射，以及独立运行的 MemoryCore Gateway 和记忆数据；只开放 B 所需的局域网入口 |
| A、B 本地连接程序 | 使用同一种 Codex 适配器观察任务；持久保存待传事件，按固定周期批量上报，收到确认后推进同步游标 |
| Codex 适配器 | 将原生事件转成统一的开始、结束、中断等记录；从本项目记忆缓存取回少量相关内容，在支持的入口提供给 Codex |
| 网页 | 展示已收到的项目、机器、任务、同步时间和项目记忆；不假装能看到尚未上报的实时状态 |

建议统一事件至少保留项目 ID、稳定机器 ID、Agent 类型、来源会话 ID、执行轮次 ID、事件 ID、来源发生时间、事件种类和原始证据。服务端另记接收时间。用稳定事件 ID 去重；同一任务的旧事件晚到时仍保留记录，但不得让最新状态倒退。目录到项目必须显式绑定，不能凭名称猜测。

## 2 先做可行性验证

在两台机器的**实际 Codex 入口和版本**上，先验证以下三件事，再开始大面积修改网页和底座：

1. 本地 hook 是否能启用并获信任；一次真实提示能否收到 `UserPromptSubmit`，结束与中断能否分别收到 `Stop`、`Interrupt`。记录 `cwd`、`session_id`、`turn_id` 可取得的实际值。Codex [官方 Hooks 文档](https://learn.chatgpt.com/docs/hooks)给出了这些事件和字段，但两机入口是否一致仍须实测。
2. B 机收到一条仅保存在 A 项目中的测试记忆后，`UserPromptSubmit` 的 `additionalContext` 能否在模型请求前提供它。保存 hook 输出及 Codex 使用该约定的证据；只检索到或只写入本地缓存均不算通过。官方文档说明该输出会作为额外上下文提供，但实际部署仍须验证。[官方 Hooks 文档](https://learn.chatgpt.com/docs/hooks)
3. 判定何种**明确来源证据**足以把一项工作标为“Agent 上报完成”。`Stop` 只能证明本轮停止，不能独自证明整项工作完成。若真实入口没有可可靠识别的完成证据，保持“本轮已结束／完成情况未知”，并把 M03 的明确完成项标为未验证，不能为了过验收猜测。
4. 在 A 上验证 MemoryCore 的项目身份映射、L3 首次写入、版本读取与服务重启后持久性；不同项目的隔离作为完整需求的单独检查，不增加本轮“一个项目”的 M04 最小验收范围。实际 API 与版本以选定源码为准。

Codex hook 需要在每台机器上实际启用并按当前定义完成信任审查；hook 回调只写本地队列或读取已缓存的少量记忆，云端网络延迟不应卡住一次 Codex 操作。当前文档把 `transcript_path` 指向的文件格式列为不稳定接口，因此不把解析它作为首选契约。[官方 Hooks 文档](https://learn.chatgpt.com/docs/hooks)

## 3 按顺序实现

1. **服务与项目关联**：从已选定、版本一致的底座源码建立第一版开发分支；在 A 启动网页、API 和数据库。建一个项目，让 A、B 各自的 Codex 工作目录关联到它；B 通过 A 的局域网地址接入。数据库只供 A 内部使用。
2. **Codex 本地采集**：同一适配器安装在两机；把提示开始、轮次结束和中断转为带来源证据的事件。无法可靠取得的标题、进展或完成说明保持未知。hook 未触发或读取失败时留下可检查的本地错误。
3. **持久队列与定时同步**：本机先落盘，再按固定周期上传新增事件；服务端逐条确认、去重并保留发生与接收时间。浏览器关闭不影响连接程序。用 B 断网、恢复、重传和旧事件晚到验证补传与状态顺序。
4. **项目记忆**：A 部署 MemoryCore Gateway，AgentHarbor 后端持有私有凭据和项目到 MemoryCore 身份的映射。网页通过 A 后端把一条项目约定写入 MemoryCore L3，B 从 A 的接口更新本项目缓存，再由 Codex Hook 在提示前提供。记录 MemoryCore 版本、缓存命中与 Hook 返回结果；按 M04 验证同项目跨机提供。自动提炼和四层自动归纳不作为本轮门槛。
5. **接上真实页面**：将现有原型中的项目、任务、机器、同步和项目记忆入口接入服务端记录。逐项运行 M01–M05；两机、真实 Codex、真实局域网同步和真实记忆提供的证据齐全后，才称第一版达到最小验收。

这条路线不需要把任务改成底座派发的运行。底座现有 daemon 主要领取并执行由平台排队的 run；用户从原有 Codex 入口直接开始的任务需要本地观察接入。[底座运行说明](https://multica.ai/docs/daemon-runtimes)

## 4 第一版完成后的推仓前检查

目前本地工作目录包含需求、原型、第三方源码和预览运行数据，不是 AgentHarbor 的 Git 工作树；[公开仓库](https://github.com/TheoEquity/AgentHarbor)目前只有 README。实施时应把第一版源代码和必要文档整理到干净的仓库工作树，完成后先检查实际差异与提交历史，再推送。

检查重点：

- 有可复现的 A 启动、B 接入说明，以及 M01–M05 的真实执行记录；未验证项明确标出。
- 不把 `.env`、凭据文件、预览日志、运行数据库、缓存或本地会话内容提交到公开仓库；检查暂存文件和 Git 历史，而不只看工作目录。
- 若复制或改动了底座源码，按其[许可证](https://github.com/multica-ai/multica/blob/main/LICENSE)保留适用的许可、署名及界面标识要求。产品页面无需写成“接入 Multica”的操作步骤，但公开分发不能隐去许可证要求的归属说明。
- 记录实际依赖的底座版本、Codex 版本和两机系统；来源代码与运行镜像版本一致。
- 记录 MemoryCore 的固定源码/镜像版本、内部凭据配置和持久化数据位置；公开仓库只保留无密钥的部署说明。

完成后提供本地仓库路径或待审分支、A/B 运行方式和验收记录，由审查者核对代码、行为、许可与公开内容，再决定是否推送。当前未进行代码审查，也未推送第一版。
