# AgentHarbor 下一阶段需求整理

整理日期：2026-11-07

状态：用户已确认采用"四类记忆 + 独立生命周期 + 项目或全局范围"的架构方向。本次只更新文档；开关默认值、自动采集范围及具体组件选择仍按下文区分建议与待定，不代表已经实现。

AgentHarbor 下一阶段需要支持按项目启停的云端记忆和任务管理：本地工作产生的材料可以先收集，经过整理后形成可复用知识；同项目的新会话和其他机器可以直接从云端取回适合使用的记忆。另增加全局通用记忆的需求方向，由用户选择哪些项目启用、哪些项目不启用。

本文补充[完整需求文档](requirements.md)，技术落点见[下一阶段技术方案](technical-design-v2.md)。两机操作仍沿用[验收与部署方案](acceptance.md)的部署方向；其中旧版 L3 与缓存读取路径被新方案替代，历史验收记录不改写为新能力已通过。

## 0 已确认的架构决定

| 记忆类型 | 职责与取回方式 |
| --- | --- |
| 工作记忆 Working Memory | 当前任务、计划、临时工具结果主要由当前智能体会话维护；云端展示必要的任务状态和交接摘要 |
| 情景记忆 Episodic Memory | 某次 Bug 修复、失败过程、任务经历；需要回顾类似问题时检索，默认不整批放进新会话 |
| 语义记忆 Semantic Memory | 已确认的目录结构、接口约束、项目事实和通用偏好；新会话读取必要的有效知识，详细内容按需取回 |
| 程序记忆 Procedural Memory | 经过验证的操作步骤、工作流、Skill；遇到匹配的任务时加载 |

四类不是四级晋升流程。另设独立维度：内容可处于候选、有效、停用或被替代状态；范围可为项目专属或本人全局通用；条目保留来源与版本。普通材料可收集但不自动生效，只有用户明确确认的事实和规则可走直接记住路径。

记忆以独立条目维护，简短核心摘要是有效条目的派生结果。保留现有项目、身份校验、任务同步和 MCP 接入基础；不要求推倒整个项目，也不为四类各建一套服务。腾讯 L0–L3 不直接等同这四类，后续按受控提炼等局部能力评估复用。

## 1 记忆收集与使用

### 1.1 普通材料可以先收集

CIS 5480 修复一个普通 Bug 后，相关经历可以先上传。上传本身不表示这段经历值得成为长期知识，也不表示以后每次会话都应该使用它。用户希望先积累材料，再统一处理。

材料还可能来自其他项目工具、外部摘录或已有记忆。发现内容有错误时，应支持收集问题、补充依据并进行纠正；未经核实的内容不能直接作为已确认事实使用。

### 1.2 整理后的知识供智能体复用

用户希望对收集内容进行筛选、核实、纠错和合并，留下确实有用的知识。新会话默认使用适合当前项目的有效记忆，普通材料不默认全部进入上下文。

任务活动与长期知识之间需要有明确转换规则。一次任务结束、一次修复完成或一份材料上传，都不自动等于知识已经生效。

### 1.3 明确的事实和要求支持直接记住

用户明确告诉智能体的项目结构、目录位置、输出规则、接口约束和做事要求，也属于需要复用的内容。智能体应能识别并记录这些信息，不必全部等待一次批量整理。

| 内容 | 期望处理 |
| --- | --- |
| 普通经历、零散材料 | 先收集，留待整理 |
| 外部内容、疑似错误的记忆 | 保留来源和待核实状态，支持纠错 |
| 整理后有复用价值的知识 | 成为有效记忆，按需提供给智能体 |
| 用户明确确认的项目事实和要求 | 支持直接记录并用于后续工作 |

用户明确要求记住且确认内容时，允许直接保存为有效条目并记录确认来源；智能体自行推断或外部摘录先进入候选。普通任务经历不会因同步成功自动生效。自动采集正文范围和整理触发时机待确定；本轮技术建议先做明确提交和用户确认，不默认每轮后台提炼。

### 1.4 全局通用记忆与项目专属记忆

用户希望增加一类适用于本人多个项目的全局记忆，例如通用的工作习惯、输出偏好和已确认的做事方法。系统应能选择哪些项目使用这套全局记忆，哪些项目不使用；具体实现方式和默认启用范围尚未确定。

| 记忆范围 | 内容示例 | 使用边界 |
| --- | --- | --- |
| 全局通用记忆 | 多个项目通用的偏好、要求、方法 | 只向启用了全局记忆的项目提供 |
| 项目专属记忆 | CIS 5480 的目录、课程约定、项目接口 | 仍限于所属项目，不因全局记忆功能而向其他项目开放 |

全局与项目表示适用范围；待整理与有效表示内容状态。全局内容也应遵循收集、核实和生效规则，不能因标为全局就把全部材料直接注入会话。

项目专属内容不能自动升级为全局知识。v2 建议全局内容由本人在全局管理入口确认写入，项目侧可提出通用化候选；具体授权方式尚未实施。启用全局记忆的使用，不自动等于获得修改全局记忆的能力。

## 2 记忆架构与存储

### 2.1 当前实现事实

当前项目接通的是 MemoryCore L3 核心记忆：每个项目对应一份核心文档，当前本机存储落在项目隔离目录中的 `persona.md`。MCP 写入会把一条会话记录追加到这份文档，读取时整份返回。网页编辑则保存整份文档。

目前没有接通完整四层处理流程，也没有实现待整理材料与有效知识的分开管理。腾讯系统具有其他层的代码，不代表 AgentHarbor 已使用这些能力。

当前接入只处理项目范围的记忆，尚未实现本次提出的全局通用记忆和按项目启用全局记忆的设置。

实现依据：[MemoryCore 客户端](../../server/internal/agentharbormemory/client.go)、[项目记忆接口](../../server/internal/handler/agentharbor_memory.go)、[记忆 MCP 工具](../../tools/agentharbor-connector/memory_mcp.py)。

### 2.2 下一阶段需要满足的能力

- 能按条查看、整理、更正或停用内容。
- 能区分待整理材料和当前可用知识。
- 能区分全局通用记忆与项目专属记忆，并按项目设置控制取回范围。
- 能追溯有效知识的来源及更新情况。
- 能提供当前会话需要的有效部分，避免持续把所有历史材料堆进上下文。

已确定以独立条目作为管理单位，不再整份 L3 追加后全量读取。v2 建议使用现有 PostgreSQL 保存权威条目、来源、状态和修订记录；供智能体读取的简短摘要由有效条目生成。该存储落点是技术方案，尚未迁移；不要求一条记忆必须等于一个磁盘文件。

## 3 上云与多机轻量接入

用户希望将服务部署到云端，开始多机同步测试。不同机器上的本地目录可以绑定同一个云端项目，共享该项目的有效记忆，同时保留机器和会话来源。

接入操作应尽量轻量：每台机器完成基础接入，每个项目完成绑定；新开会话不需要重复维护一套脚本、环境变量或工具配置。日常记录继续支持固定周期批量上传，不要求持续实时传输。

当前记忆读写入口是 MCP，工具再通过 HTTP 访问 AgentHarbor；任务采集通过本地 Hook 写队列，连接程序每 30 秒通过 HTTP 同步。v2 建议保留这套分工，将绑定与配置集中到一个本机连接程序：任务和材料定时上传，MCP 按需读写，新会话自动读取另由适配入口触发。MCP 不是队列同步协议，也不会仅因安装就自动在新会话读取。

实现依据：[记忆 MCP 工具](../../tools/agentharbor-connector/memory_mcp.py)、[任务连接程序](../../tools/agentharbor-connector/connector.py)。

跨机要求延续项目隔离：绑定其他项目的智能体不能读取或写入 CIS 5480 的项目记忆。记忆取回应直接访问服务，不要求用户指定或寻找本地缓存文件。

全局记忆通过明确的项目启用设置提供共享内容；这不改变项目专属记忆的隔离边界。

## 4 Codex 任务接入

用户希望把现有 Codex 任务或会话记录接入 AgentHarbor。用户继续在本地开展工作，网页按项目查看哪台机器、哪个智能体、哪个会话在做什么，以及最近状态和同步时间；继续保留不从看板派发任务的范围约束。

当前任务页已有项目、机器、智能体、会话标识、最近状态、事件发生时间和服务端接收时间。现有连接程序主要采集启用 Hook 后的新事件，没有实现历史会话扫描；`Stop` 只表示本轮结束，不能据此认定任务完成。

实现依据：[任务连接程序](../../tools/agentharbor-connector/connector.py)、[智能体任务页面](../../packages/views/agentharbor/agent-tasks-page.tsx)。

用户本次提到的现有 Codex 任务，具体来自先前的任务监控器还是 Codex 桌面会话列表，仍需核对。任务产生的经历可以进入待整理材料，是否沉淀为有效知识遵循第 1 节规则。

## 5 项目开关与新会话读取

### 5.1 需要表达的设置意图

用户需要在本地为项目开启或关闭记忆相关功能，并选择是否把它交给云端知识库同步和维护。设置应持续作用于后续会话，不必每次重新配置。

至少需要分清以下设置意图；v2 提供最小控件与作用范围建议，默认值还不是用户决定。

| 设置意图 | 需要明确的行为 |
| --- | --- |
| 是否记录记忆 | 后续工作是否继续产生待整理材料或记忆写入 |
| 是否同步到云端维护 | 项目内容是否进入云端同步与整理流程 |
| 是否让智能体使用记忆 | 后续会话是否自动读取和使用已有知识 |
| 本项目是否使用全局记忆 | 系统可选择对哪些项目提供全局通用知识；停用后不再为该项目取回全局内容，项目专属记忆仍由原有设置控制 |

### 5.2 已启用项目的新会话

用户在已启用的项目中新开会话时，希望必要的有效记忆直接从云端读入。日常上传采用固定周期，与新会话读取最新有效知识的触发时机可以分开。详细历史材料再按需要检索。

取回内容应遵循项目设置：项目专属记忆保持项目隔离；只有启用了全局记忆的项目，才同时取回适用的全局有效知识，并能区分其来源范围。关闭全局记忆使用不会删除共享内容，也不会替其他项目关闭该能力。

当前 MCP 只在工具被调用时发起请求，本身不保证新会话自动取回。仓库原有连接程序还包含按提示注入本地缓存的逻辑；这不等于已经实现本节要求的新会话直接读取云端，后续需要统一实际生效的接入路径。

### 5.3 关闭及重新开启

关闭需要停止后续对应的记录、同步或读取，已有云端数据可以保留。重新开启后应恢复已选功能。已进入当前会话上下文的内容，不能承诺通过关闭开关立即消除。

建议区分"本机暂停"和"项目规则"：本机暂停只影响本机，云端项目停用阻止各机器后续对应读写；状态页显示二者。停用不删除旧记忆，待传材料保留但停止发送，重新启用前明确是否继续补传。此处是 v2 建议，待传处理与开关默认值仍需在实施前确认。

建议本地绑定时提供首次选择及本机暂停入口，云端「项目记忆 → 设置」维护项目规则；「设置 → 全局记忆」维护通用内容。无需每个会话重复配置，不修改项目 `AGENTS.md`。

## 6 本地与云端冲突

需要同时处理同步冲突和内容冲突。

- 同步冲突：不同机器同时提交时，新增记录不能互相覆盖或丢失；旧版本不能悄悄覆盖已更新的有效知识。
- 内容冲突：云端记忆可能与本地代码、目录结构、当前明确要求或另一条知识矛盾。应能发现、标出并纠正或停用过时内容，避免把矛盾信息都当作事实继续使用。

有效知识保留来源和版本。v2 建议通过独立新增、幂等标识和旧版本校验防止同步覆盖；对内容矛盾先核对当前代码或原始依据，再提出更正，不能把写入时间更新当作事实更可靠。全局通用偏好可由明确的项目约定细化，但两条事实相互矛盾时不能仅按范围或时间自动裁决；相关规则仍需实际场景验收。

继续保留用户已提出的约束：通过接入机制提供记忆，不修改项目的 `AGENTS.md`。

## 7 目标操作流程

以下是希望实现的操作流程，不表示当前页面和接入程序已经全部支持。

1. 用户在本机选择 CIS 5480 的工作目录，并绑定云端同一项目。
2. 用户选择是否记录、是否上云维护、是否让后续会话使用记忆，并在系统中选择 CIS 5480 是否使用全局通用记忆。
3. 用户照常在本地使用 Codex，任务状态按固定周期同步。
4. 普通经历和外部材料进入待整理内容；明确的项目事实和要求支持直接记录。
5. 用户在云端统一整理材料，形成有效知识；具体自动化程度待定。
6. 本机或另一台机器在同项目中新开会话时，自动取回必要的项目有效记忆；仅在该项目启用全局记忆时，一并取回适用的全局有效知识。
7. 用户随时暂停或重新开启所选功能，既有数据按已确定的保留规则处理。
8. 出现同步或知识内容冲突时，用户能查看来源和版本，完成处理。

## 8 待定事项与建议推进顺序

| 待定事项 | 需要决定的内容 |
| --- | --- |
| 收集与沉淀 | 哪些正文自动收集、自动整理何时触发；本轮先按明确提交、用户确认生效设计 |
| 直接记住 | 已明确用户确认可直接生效；智能体自行判断的自动生效不在本轮范围 |
| 全局记忆 | 默认对哪些项目启用；v2 建议本人确认全局写入，需落实授权与通用化操作 |
| 开关语义 | 记录、云端维护、使用记忆的组合方式及默认值 |
| 开关作用范围 | 本机暂停与全项目停用如何区分；待传内容如何处理 |
| Codex 任务来源 | 现有监控器、桌面会话列表或其他实际来源 |
| 接入与存储 | v2 提供 MCP/HTTP 分工和 PostgreSQL 条目方案；启动入口兼容性、腾讯可复用模块仍需实现前验证 |
| 冲突规则 | 并发更新按版本拒绝覆盖；内容矛盾如何提示和更正按 v2 建议验证，不宣称自动解决所有冲突 |

后续按 v2 分阶段推进：先完成条目与状态的本机闭环，再接新会话和项目开关，最后上云进行两机验收与自动提炼评估。当前只完成需求与技术文档更新，未开始本轮架构改造。
